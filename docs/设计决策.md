## 二、货币与经济（老板已确认的细节）

1. **六种货币**：每家公司一种**票据**（`<company>_scrip`），**不通用**。
2. **跨公司兑换有汇率**：公司之间的汇率不同（数据包可配），产生跑商空间。
3. **钱平时存在各公司的商店方块里**：商店方块自带金库（方块内保存现金 NBT）。
4. **银行卡（`bank_card`）**：玩家用卡在商店方块存取；卡里按公司分别记账；
   也可**取现**成票据物品，用于玩家之间当面交易。
5. **商店开机条件**：右键商店方块 → **插入银行卡**（卡里有没有钱都行）→ 方块"开机"（亮灯/可用）。
6. **收购方块**（新增的功能方块）：专门负责"投入物品 → 换钱"，**支持机械手/传送带自动化投入**。
7. **价目表放数据包 JSON**：可买物品、可买物理结构、价格、收购清单都能改，不用重编译。
8. **游戏内编辑器**：ESC 菜单左侧新增一个按钮（**仅管理员/OP 可见可开**），
   用 UI 直接改价格表、商品、物理结构列表、收购清单。
9. **定价**：按公司 / 工厂等级**差异化定价**（低级厂收购价低、高级厂高）。
10. **购买门槛**：工厂等级 + 公司声望（累计消费）**双重解锁**。
11. **组装配方**：蓝图材料 + 信用点（该公司票据）+ 组装时间，三者都要。
12. **权限**：任何人可用，**按发起者扣费**（多人共用一座工厂没问题）。

### 2.1 银行卡 = 账户指针（老板后加的设定，已实现）

13. **右键银行卡**打开"绑定账户"界面，填写**玩家名或 UUID** 把卡绑到那个玩家的账户；
    界面里也有「解除绑定」。卡上会显示"账户：XXX"。
14. **钱按玩家分账存在商店方块里**：每个方块、每家公司、每个账户各一份「方块内本地余额」。
    同一个方块里 A 存的钱和 B 存的钱是分开记的。
15. **插卡进方块 = 选定账户**：之后所有操作都以这张卡绑定的账户为准。
16. **花钱优先级**：购买时**先扣方块里该账户的本地余额**，不够再扣**卡上余额**。
17. **卡留在方块里没取走，别人也能用**：其他玩家右键这台机器就能用这张卡买东西，
    花的是**卡主账户**的钱（等于"公户卡"/公司信用卡）。这是有意设计的玩法，不是漏洞。
18. **卡上余额 vs 方块内余额**：
    - 方块内余额 = 实物票据的记账，**可以取现**；
    - 卡上余额 = 便携数字余额（来自跨公司兑换），**只能用于购买与兑换，不能取现**（防刷钱）。
19. 没绑定的卡**第一次插进方块时自动绑到插卡的人**，所以单人玩不受影响。

### 2.2 商店 / 收购站 / 声望（M2 已实现）

20. **价目表在数据包里**：`data/deepspacedeployer/shop/<公司代号>.json`，每家公司一份，格式：

    ```json
    {
      "company": "skimmer",
      "buy":  [ { "item": "aeronautics:andesite_propeller", "count": 1, "price": 190, "tier": "low", "reputation": 0 } ],
      "sell": [ { "item": "minecraft:iron_ingot", "count": 1, "price": 8 } ]
    }
    ```

    - `buy` = 公司**卖给玩家**（工厂终端里按页显示，可翻页、可购买）
    - `sell` = 公司**收购**（收购站按这张表换钱）
    - `tier` = 需要的工厂等级（low/mid/high）；`reputation` = 需要的声望
    - 改完在游戏里 `/reload` 生效，多人服务器不用重启
    - 物品 id 写错只会被跳过并记日志，不会崩

21. **等级差异化定价**：收购价 = 表里的价格 × 等级倍率（低级 0.8 / 中级 1.0 / 高级 1.2）。
    这就是"低级厂压价、高级厂溢价"。
22. **声望**：累积消费 ÷ 1000（可配）= 声望点，按**玩家 × 公司**分别记录，存在世界存档里。
23. **收购站自动化**：9 个输入格 + 每 10 tick 结算一次；漏斗和机械手都能往里塞
    （已注册 NeoForge 物品能力，只暴露输入格，银行卡格永远取不出来）。
24. **购买校验顺序**：等级 → 声望 → 余额（先方块内、再卡上）；成功后给货并累加声望。
25. **调试手段**：创造模式**潜行右键**方块可以轮换"公司 + 等级"（6 家 × 3 级循环），
    等 M5 世界生成做好后由建筑决定，这个调试入口会保留但不影响正常玩法。

### 2.3 工厂方块：蓝图组装（M3 已实现）

26. **蓝图来源**：服务器文件夹 `config/deepspacedeployer/blueprints/*.nbt`
    （就是机械动力的蓝图文件，格式是原版结构 NBT）。服务器启动自动读取；
    改完文件用管理员指令 `/dsd reloadblueprints` 重新读（需要 OP）。
27. **界面两页**：
    - 「蓝图」页：列出所有蓝图（名字 / 尺寸 / 方块数），点「选」选中
    - 「材料/组装」页：显示该蓝图每种材料的 **有/需**（绿的够、红的缺），以及组装费
28. **投料**：工厂核心有 9 个投料格，放进去的物品每 10 tick 被吸进"材料缓冲"（按物品记账，不占格子）。
29. **一键组装**的校验顺序：先选蓝图 → 材料是否齐 → **前方 3 格场地是否够空** → 扣组装费 → 扣材料（转为预留）。
    场地检查放在扣钱之前，避免白花钱。
30. **组装费**：`每方块组装费（默认 20）× 蓝图方块数`。组装耗时按等级：低级 20 秒 / 中级 12 秒 / 高级 6 秒。
31. **等级上限**：低级厂最多造 200 方块、中级 800、高级 4000（硬上限还有配置项 `max_blueprint_blocks`）。
32. **落地位置**：现在是"**机器正面 3 格、按蓝图尺寸居中**"（朝玩家看向的方向）。
    地图选点（Xaero）留到后面做——Xaero 没有公开 API，需要另做方案。
33. **取消组装**：材料退回缓冲，**组装费不退**（当作开工成本）。
34. **组装完成**：结构直接落地（含方块实体 NBT），附近 64 格内的玩家会收到提示。
    如果那一刻场地被堵住，材料退回缓冲并广播失败。
35. **示例蓝图**：工程里 `examples/blueprints/` 有两份（`test_platform` 5×3×5 / `small_airship` 9×6×7），
    由 `python tools/gen_example_blueprints.py` 生成并自动复制到游戏目录，方便立刻测试。

### 2.4 世界生成：18 座工厂（M5 已实现）

36. **建筑规格**（`tools/gen_factory_structures.py` 生成）：
    | 等级 | 尺寸 | 内部机器 | 生成密度（spacing/separation） |
    |---|---|---|---|
    | 低级 | 9×5×9 | 商店 + 收购站 | 40 / 14（最常见） |
    | 中级 | 13×7×13 | + 工厂核心 | 60 / 22 |
    | 高级 | 17×9×17 | + 焊接台 | 90 / 34（最稀有） |
37. **公司共用一个等级池**：同一等级里 6 家公司权重相同，所以同一个群系可能刷出任意一家公司。
38. **机器是从蓝图里就带好公司/等级属性的**（方块状态 `company=xxx,tier=yyy`），所以
    "低级厂只卖基础货、高级厂才有高级货"在世界生成里天然成立。
39. **箱子里有本公司票据**（低级 17 张 / 高级 25 张），落地就能开始消费。
40. **群系分布**：低级→平原/森林类；中级→沙漠/针叶林/丘陵类；高级→山地/极端类。
    标签里同时写了**原版群系**和**你整合包里的 BiomesOPlenty 群系**（薰衣草田、林地、高地等），
    所以在你的整合包里能真的刷出来。
41. **方块外观**：4 种机器 × 6 公司 × 3 等级 = **72 种外观**（+点亮版共 144 张贴图），
    公司色做主色调、等级用左下角 1/2/3 个金色小点 + 高级加金边区分。
42. **测试用指令**：`/place structure deepspacedeployer:factory_skimmer_high`（直接放一座在你脚下）、
    `/locate structure deepspacedeployer:factory_threshold_low`（找最近的一座）。
    注意：**已探索过的区块不会补生成**，要看自然生成得去新区域。

### 2.5 焊接台与物理结构（M4 已实现）

43. **焊接台作用**：把"工厂刚造出来的那份蓝图结构"焊成一个**物理结构**（Sable 的 SubLevel）。
    找不到附近刚组装完的工厂核心时，退化成"焊接自己连着的结构"（适合焊玩家手搭的小玩意）。
44. **组装即物理化**：工厂组装完成、方块落地之后，会顺手调用 Sable 的组装接口把它变成物理结构
    （配置项 `factory.assemble_as_physics`，默认开；失败不影响方块落地，只多一条提示）。
45. **开关碰撞：只有高级焊接台有**（老板定的规则）：
    - 低级/中级点了会被挡下来并提示"只有高级有"
    - 高级点了会调用 Photomancy 的 `RuntimeSubLevelStaticService.setStatic(...)`，
      静态 = 冻结（不参与物理），动态 = 正常物理
46. **全部走反射**，理由：Sable 的 API 在演进、Synaxis 闭源、Photomancy 自己声明 API 不稳定。
    好处是没装这些模组时模组照样能跑，找不到方法只会在日志里写清楚原因，不会崩。
47. **诊断指令 `/dsd integration`**：打印
    - 相关模组装了没有（create / aeronautics / simulated / sable / sable_schematic_api / synaxis）
    - 关键类能不能加载，**并列出它们的公开静态方法签名**
    - 我们两个桥（Sable 组装 / 无碰撞开关）各自的状态
    服务器启动时也会把同一份报告写进日志（搜 `[深空铸造体][联动]`）。
    **这份输出的作用**：如果某个联动没生效，把它发给我，我就能按真实签名把调用精确对上。
48. **焊接参数**：一次最多 512 个方块（`welder.max_blocks`），搜索半径 24 格（`welder.radius`）。
49. 焊出来的结构 id 会存在焊接台里；子层级 id 也用于"开关碰撞"（没有 id 时提示先焊接）。

### 2.6 游戏内价目表编辑器（M6 已实现）

50. **入口**：ESC 菜单**左侧**多一个「价目表编辑器」按钮，**只对 OP（权限等级 2）显示**；
    权限在服务端也会再查一遍，普通玩家就算发假包也改不了。
51. **界面能做什么**：
    - 顶部六家公司切换（当前公司高亮）、「公司出售 / 公司收购」两张表切换
    - 每行：物品图标 + 名字 + 价格 + `-5` / `+5` 调价 + 「等级」按钮（循环 low→mid→high，只对出售表有效）+ 「删除」
    - 底部：翻页、「加入商品」（把手里的物品按默认价 100 加进出售表）、
      「加入收购」（默认价 10）、「保存」、「关闭」
52. **改动立刻生效**（服务器内存里的价目表当场换掉，所有商店马上按新价走），
    点「保存」才写文件。
53. **保存到哪**：`<存档>/datapacks/deepspacedeployer_editor/data/deepspacedeployer/shop/<公司>.json`
    （顺带写 `pack.mcmeta`），保存后自动触发数据包重载，所以：
    - 重启游戏 / 重启服务器都不会丢
    - 想手改也行 —— 就是普通数据包文件
54. 也就是说：**内置默认表 →（游戏内改）→ 世界数据包**，世界数据包优先级更高，覆盖同公司的表。

### 2.7 诊断与稳健性（第 6 轮加固）

55. **`/dsd selftest`**：一次性自检（注册 / 价目表物品 id / 蓝图 / 配置 / 声望存档 / 联动），
    同时写进日志（搜 `[自检]`）。进游戏第一件事就该跑它。
56. **机械动力的依赖从 required 改成 optional**：我们的代码并不 import Create 的类
    （蓝图＝原版结构 NBT，商品＝数据包里的 id 字符串），所以没装 Create 也能进游戏；
    只是价目表里 `create:` 的条目会被跳过，`/dsd selftest` 会把它们列出来。
57. **方块实体的"机器种类"改成进世界时缓存一次**：原来每次都读方块状态，而读方块状态需要 `level`，
    在方块实体还没挂到世界上的极早期调用会空指针 —— 这是本轮修掉的一个真实崩溃隐患。
58. 新增配置 `factory.physics_max_blocks`（默认 4096）：物理化时最多收集多少方块。
59. 工程侧还有 `python tools\validate.py`：交叉验证贴图/模型/方块状态/语言键/18 份结构 NBT/世界生成链路。

### 2.8 商店卖"物理结构使用权"：蓝图凭证（第 7 轮）

60. **新物品「蓝图凭证」**（`blueprint_voucher`）：卡上带着"这是哪份蓝图"的数据。
61. **买法**：价目表 `buy` 里多一个可选字段 `blueprint`：
    ```json
    { "item": "deepspacedeployer:blueprint_voucher", "count": 1, "price": 900, "tier": "low", "reputation": 0, "blueprint": "test_platform" }
    ```
    不带 `blueprint` 的凭证是无效的（工具提示会写明）。
62. **用法**：拿着凭证对**工厂装配核心右键** → 该核心直接选中这份蓝图，凭证消耗掉；
    之后照常投材料 + 一键组装。凭证**只解锁图纸，不含材料**。
63. **兜底**：如果服务器上没有这份蓝图文件，使用时提示"服务器上没有这份蓝图"并**不消耗**凭证；
    `/dsd selftest` 也会把"凭证指向了不存在的蓝图"列出来。
64. **默认报价**：阈限实验集团和掠影推进公司各卖两份（`test_platform` 900/1100 起，`small_airship` 3200/3600）；
    其他公司只卖模块 —— 你可以在数据包或编辑器里随时加。
65. 编辑器里"加入商品"现在也能识别**手里拿的凭证**（连蓝图名一起记下来，且不会和不同蓝图的凭证判重）。

### 2.9 投放点自己选：俯视图选点（第 8 轮）

66. **为什么自己做地图**：老板本来想用 Xaero 地图选落点，但 Xaero 没有对外 API。
    所以改成**自己做一张俯视图**：客户端采样 `WORLD_SURFACE` 高度图 + 每个方块的**地图颜色**
    （`BlockState#getMapColor`），按高度做明暗，生成一张 1 方块=1 像素的贴图（半径默认 48 → 97×97）。
67. **交互**：材料页点「选投放点」→ 地图上蓝框是机器、点哪儿金框就落哪儿 →
    「确认投放点」把坐标发给服务端（`SetAssemblyTargetPayload`）。
68. **服务端校验**：距离超过 `factory.assembly_max_radius`（默认 48）直接拒绝；
    结构以落点为中心展开，高度取机器那一层。
69. **不选就还是老行为**（落在机器正面 3 格），选了会显示"投放点：已在地图上选定"。
    投放点存在方块实体里，重启也在。
70. 用到的渲染 API：`NativeImage#setPixelRGBA`（ABGR）→ `DynamicTexture` → `TextureManager#register`
    → `GuiGraphics#blit`，界面关闭时 `release` 掉贴图。

### 2.10 对着反编译源码做的验证与一个真 bug（第 9 轮）

71. **重要工具**：ModDevGradle 构建时会产出**反编译后的 Minecraft + NeoForge 源码**：
    `build/moddev/artifacts/neoforge-21.1.248-sources.jar`（9 MB，6300+ 个 .java）。
    以后遇到"这个 API 到底怎么表现"的问题，直接读它，不要猜。
72. **修掉一个会让整个蓝图系统失效的 bug**：原来用
    `StructureTemplate#filterBlocks(pos, settings, null)` 枚举蓝图方块，但原版实现是
    `state.is(filter)`，而 `BlockStateBase#is(Block)` 就是 `getBlock() == block` ——
    **传 null 时一个方块都匹配不到**。后果：材料清单永远是空的（甚至异常导致蓝图整份被跳过），
    工厂界面里会"看不到任何蓝图"。
    现在改成**自己读结构 NBT**（`BlueprintParser`）：`size` / `palette`（也兼容 `palettes`）/ `blocks`
    → 材料表 + 非空气方块坐标。场地检查也用这份坐标，不再依赖那个过滤器的边角行为。
73. **顺手验证的四个高风险假设**（都读了源码，结论都是"我写对了"）：
    - `IContainerFactory` 的两参数兜底是 `create(id, inv, null)` —— **传 null 不会抛异常**，
      所以我们用单参数 `openMenu` + 不读 buffer 的客户端工厂是安全的（界面不会崩）

### 2.13 又抓到一个真 bug：右键顺序（第 12 轮）

85. **原版右键的执行顺序**（`ServerPlayerGameMode#useItemOn`）：
    ```
    方块.useItemOn  →  （若返回 PASS_TO_DEFAULT_BLOCK_INTERACTION）方块.useWithoutItem  →  物品.useOn
    ```
86. **问题**：机器方块在 `useWithoutItem` 里是"打开界面 + 消费交互"，所以**手持授权铭牌 / 升级套件 /
    蓝图凭证右键机器时，只会弹出界面，物品效果永远不触发**（蓝图凭证从第 7 轮起就一直是坏的）。
87. **修法**：加了一个标记接口 `MachineTargetItem`（铭牌 / 套件 / 凭证实现它）。
    机器方块的 `useItemOn` 看到这类物品时返回
    `ItemInteractionResult.SKIP_DEFAULT_BLOCK_INTERACTION` —— 它既不消费（`consumesAction()=false`），
    也不是 `PASS_TO_DEFAULT_BLOCK_INTERACTION`，所以会**跳过 useWithoutItem**，把这次右键让给物品自己 ✓。
88. **顺带**：玩家潜行右键时原版会跳过物品的 `useOn`，所以用这些物品时**别按 Shift**（工具提示里已说明用途）。

### 2.18 拆机器不掉东西（第 16 轮）—— 目前最严重的一个 bug

107. **问题**：工程里**根本没有掉落表**（`data/deepspacedeployer/loot_table/` 不存在）。

### 2.28 修"改价格会卡一下"（老板反馈）

143. **病因（两条，第一条是真 bug）**：
     1. `ShopEditor.handle()` 里 `ACTION_SAVE` 只是 switch 的一个分支，而 `save()` 末尾那句
        `server.reloadResources(...)` 是**无条件执行**的 —— 于是**每点一下 +1/-1、切等级、删一行、
        点确定**都会做一次**完整的服务器数据包重载**：重新读盘解析整合包里所有配方/战利品表/标签，
        换掉资源管理器、给所有玩家重发配方。而且原版 `reloadResources` 在服务器线程上会走
        `managedBlock(...)` 把主线程卡住等它完成 —— 整合包越大卡得越久（几百毫秒到好几秒）。
        **修**：`save()` 只从 `ACTION_SAVE` 分支调用，并且改成 `server.execute(() -> reload...)`
        排队执行 + 结束时打一条耗时日志；保存时明确提示"正在重载、会卡一下"。
     2. 客户端 `ShopEditorScreen.tick()` 只要看到数据版本号变了就 `rebuildWidgets()`，
        而每次改价格服务端都会回推一整张表 → 整套控件（含价格输入框）被重建，
        正在输入的框会掉焦点。**修**：行数没变时不再重建，只把各输入框刷新成服务端权威价格；
        服务端那边也改成**只有增删行才回推整张表**（改价格/改等级不再回推）。
144. **改完之后的行为**：点 +1/-1 / 确定 / 切等级 / 删行 —— 立刻生效、**不再卡**；
     只有点「保存」会有一次数据包重载的卡顿（日志里能看到实际耗时）。

### 2.30 创造板条箱 = 无限材料；收购站提速（老板要求）

149. **老板原话**：*"当工厂装配核心旁边有创造板条箱时视为无限材料，不消耗金额无组装时间立刻放置，

151. **判定走反射**（和 Sable / Synaxis 那些桥一个路子）—— 因为 `build.gradle` 里 Create 是
     **注释掉的**、代码里一行 `com.simibubi.create.*` 都没有，mods.toml 里也把 create 标成 optional。
     新增 `integration/CreativeCrateBridge`，**签名对着 create-1.21.1-6.0.10.jar 的真实字节码核对过**：
     ```
     CreativeCrateBlockEntity.filtering : FilteringBehaviour   （包私有字段，setAccessible）
     FilteringBehaviour.getFilter() -> ItemStack               （public）
     ```
     类名比对用字符串（比 `isInstance` 更稳），`ClassNotFoundException` / `ReflectiveOperationException` /
     `RuntimeException` / **`LinkageError`** 全部接住（字段类型缺失时抛的是 Error，不是 Exception）。
152. **三个效果**（`factory.creative_crate_infinite` 开关，默认开；半径 `factory.creative_crate_range` 默认 5 格）：
     - **材料无限**：跳过"材料够不够"检查；预留表照蓝图填，但不从缓冲扣；
       **失败/取消时不退材料**（没扣过，退了就是凭空生材料）；

     默认每 20 tick（1 秒）重扫一次，**界面打开时强制刷新**（`DATA_CREATIVE` 数据槽，走 `creativeMode(true)`）。
154. **收购站提速**：`serverTick` 原来统一 `gameTime % 10 == 0` 才动一次（每 10 tick 一格）。
     现在拆开：工厂核心仍是每 10 tick 一步（组装进度按 10 tick 步进），
     收购站改成**每 tick 结算 N 次**（`buyer.batches_per_tick`，默认 **10**，可调 1~100）；
     某一批没东西可收就提前跳出，不空转。等于投料**当 tick 就能全换成钱**（原来最多等 0.5 秒）。

     | 别人用你的卡买东西 | 东西进**使用者**背包，钱从**卡主**账户扣 | `buyOffer` → `tryPay(price, card)`；`activeAccount()` = 卡主主账户 |
     | 别人用你的卡在收购站卖东西 | 钱进**卡主**账户 | `processBuyer` → `addLocal(activeAccount(), …)` |
     | 别人用你的卡转给第三人 | 从**卡主**账户出钱 | `transferTo` 用 `CardData.ownerAccount(card)` |
176. **但查出一个真漏洞**：`CardBinding.handle` 原先注释写着"不要求是卡主"，而且
     **绑定/解绑/改名都没有归属校验** —— 拿到卡的人只要右键一次、填自己名字，就能把卡**改绑到自己名下**，
     从此原卡主在这家公司的账户就任他花。这比"花一次钱"严重得多（是**账户接管**）。
177. **修法**（老板选的口径：保护 + 解绑也不许别人做）：在 `CardBinding.handle` 最前面加一道校验 ——
     **已绑定的卡，只有卡主本人能改名 / 改绑 / 解绑**；别人点会被明确拒绝并提示
     「这张卡已经绑定给 XXX —— 卡可以借给别人用，但只有卡主本人能改名/改绑/解绑」。
     没绑定的卡仍然是谁先绑就是谁的（正常领卡流程）。
     另外卡片的物品提示会多一行「借用可以：买的东西归使用者，扣款走卡主账户；只有卡主能改绑」。

### 2.43 新增装饰方块「通用终端」（GeckoLib 模型 + 放置动画）

231. **老板要求**：*"新增一个方块，建模在桌面的星舰计划里，名字叫通用终端，

232. **源文件与格式**（先看清楚再动手）：
     | 文件 | 格式 | 用途 |
     |---|---|---|
     | `星舰计划\通用终端.bbmodel` | `java_block` | 静态方块模型，**用来取贴图** |
     | `星舰计划\动态模型\通用商店终端.bbmodel` | **`geckolib_model`** | 40 个立方体 + 1 段「放置」动画 |
     40 个立方体里**27 个带各自的旋转**、34 个尺寸不是 0.5 的整数倍 ——
     原版方块模型做不到"元素级旋转"，所以**只能走 GeckoLib**。
     而整合包里正好有 `geckolib-neoforge-1.21.1-4.9.3.jar`。
233. **写了个转换器** `tools/bbmodel_to_geckolib.py`：`.bbmodel` → GeckoLib 的
     `geo.json` + `animation.json` + 贴图 png。转换要点（都踩过）：
     * **坐标**：bbmodel 以方块中心为 (0,0)，原版/GeckoLib 的原点在方块西北下角 → x、z 各 **+8**；
     * **UV**：bbmodel 贴图原点在左上、原版在左下 → v 用 `贴图高 - v` 翻一下；
     * **方块**：`from` 可能大于 `to`，统一取 min/size；带旋转的必须给 `pivot`；
     * **骨骼名**：`outliner` 节点里**根本没有名字**（只有 uuid），名字藏在动画的 `animators` 里 ——
       所以建了一张显式映射表（`主机→main`、`爪1..4→claw1..4`、`底座→base`、`固定爪→claw_mount`），
       动画和几何共用同一张表，保证两边对得上；
     * **元素数校验**：脚本会比对"生成立方体数 == 源模型元素数"（这次 40 == 40 ✓），
       第一版只生成了 36 个，就是这个校验抓出来的（漏了嵌套骨骼下的元素）。
     生成结果：3 个顶层骨骼 / 40 个立方体 / 1 段 `放置`（length 0.41667 秒，loop hold）。
234. **动画内容**（转换后在 `animation.json` 里）：`main` 的位置 y 从 **-9 → 0**（升起），
     四只爪子绕轴转 **∓67.5°** 再落 1 像素 —— 就是"终端从地里升起来、爪子张开"。
235. **怎么进游戏**：
     * `UniversalTerminalBlock`（`RenderShape.INVISIBLE`，几何交给方块实体渲染器）+ 方块实体 + `GeoBlockRenderer`；
     * 用官方的 `DefaultedBlockGeoModel`，它按固定规则拼路径，所以文件放在
       `geo/block/…`、`animations/block/…`、`textures/block/…`（路径规则是从字节码里核对出来的，
       不是猜的：`block/` + path + `.animation.json`）；
     * **只在"刚放下"那一小会儿播动画**：放置时间记在 NBT，客户端 tick 判断

       这样退出重进世界不会又莫名其妙升一次。
236. **GeckoLib 做成可选依赖**（沿用本模组一贯做法）：

     * 拦这个"类加载"很关键：直接 `new UniversalTerminalBlock(...)` 的话，
       没装 GeckoLib 会在类验证阶段直接崩。

     路径变成 `å¢åå±æº` → "文件不存在" → 依赖没生效（编译报一堆"程序包不存在"）。

### 2.44 【事故复盘·4】通用终端把游戏卡在加载界面（GeckoLib 资源两处不合规）

240. **现象**（老板）：*"卡在加载界面进不去游戏了，你做了什么"* —— 不是崩溃，是卡住。
     日志里两条错误，都指向我新生成的文件：
     ```
     GeckoLib: Unable to parse animation: 放置
       JsonParseException: Invalid keyframe data - multiple starting keyframes?0
     deepspacedeployer:geo/block/universal_terminal.geo.json: Error loading model file
       ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0
         at RenderUtil.arrayToVec ← BakedModelFactory.constructBone
     ```
     资源重载抛异常 → Minecraft 那句"Caught error loading resourcepacks, removing all selected
     resourcepacks" → 加载界面就卡住了。
241. **根因一：关键帧顺序**。GeckoLib 的 `BakedAnimationsAdapter.buildKeyframeStack` 是
     **按顺序逐帧算"和上一帧的时间差"**的（第一帧以上一帧 = 0 参与计算）。
     `.bbmodel` 里同一通道的关键帧是按**文件顺序**给的，我这个模型里 `position` 的
     `0.25` 排在 `0` 前面 → 第一帧就出现"多个起点"而报错。
     修法：写 JSON 前**按时间数值升序重排**，并保证第一帧在 0。
242. **根因二：骨骼 / 立方体的字段缺失**。`BakedModelFactory.constructBone` 会
     **无条件**读 `bone.rotation()` 和 `bone.pivot()`（反汇编确认：`Bone.rotation()` → `RenderUtil.arrayToVec`），
     而 GeckoLib 的反序列化对缺失字段给出的是**空数组** → `arrayToVec` 直接越界。
     修法：`pivot` / `rotation` **永远写全**（没旋转就写 `[0,0,0]`），骨骼和立方体都一样。
243. **根因三（最坑的）：我一直在看错文件**。GeckoLib 的 `DefaultedBlockGeoModel` 把路径拼成
     `geo/block/<名>.geo.json`、`animations/block/<名>.animation.json`，
     而我的转换脚本输出到 `geo/<名>.geo.json`、`animations/<名>.animation.json` ——
     **少了 `block/` 那一层**。我手工把最早生成的文件挪到了正确位置，之后每次重跑脚本
     都在往**另一个路径**写新文件，于是一直在"修脚本 → 没变化 → 再修脚本"里打转。
     修法：脚本输出路径改成带 `block/`；判断"改动有没有生效"要**看时间戳/字节数**，
     不能只看脚本自己打印的成功信息。
244. **验证**：转换后的资源自查（写进本轮核对脚本）：
     10 条动画轨道**全部时间升序且首帧为 0** ✓；40 个立方体、骨骼与立方体的
     `pivot`/`rotation`/`origin`/`size` 全齐、UV 全有 ✓。
     `gradle build` 成功；`validate.py` 全过；jar 已装机（549,348 字节）。
245. **教训（写下来给自己）**：
     ① 转换/生成类脚本，产物路径要**先和消费方（这里 GeckoLib）的规则对齐**，再写生成逻辑；
     ② 验证"文件是否真的更新"要看**时间戳或内容摘要**，脚本打印"成功"不代表写对了地方；
     ③ 外部库的格式要求要么查它的字节码/源码，要么拿最小样例试，别凭印象。

### 2.45 通用终端改用**原版方块模型**（放弃 GeckoLib 那条路）

246. **老板的决定**：GeckoLib 那条路的 geo/UV 一直对不齐、模型显示不全，
     与其对着 GeckoLib 的面绕序逐面逆向，**先用原版方块模型一次做到位**（代价：没有动画）。
247. **查过 Create 那条路**（老板建议"看看机械动力怎么实现的"），学到：
     * Create 用的是 **Flywheel**（嵌在 create jar 里：`META-INF/jarjar/flywheel-neoforge-1.21.1-1.0.6.jar`），
       和 GeckoLib 是**两套完全不同的渲染栈**；
     * Create 的 `entityCutoutBlockMipped()` 用的是 `RenderType.create(..., createCompositeState(true))`
       —— 那个 `true` 是"按朝向排序"，**背面剔除仍然是默认打开的**。
       所以我原先"Create 关了剔除所以不丢面"的猜测是**错的**，问题确实在我那份 geo.json 的面/UV 上；
     * Flywheel 的动画是**用 Java 代码写**（`DynamicVisual` 每帧 transform），不是数据驱动，
       没法直接搬。
248. **新的转换器** `tools/bbmodel_to_vanilla_model.py`：静态 `.bbmodel` → 原版方块模型 JSON。
     转换要点：
     * **坐标不平移**：`java_block` 格式的坐标本来就是方块坐标系（源文件里就是 `from=[7,1.5,6]`），
       和原版一致（原点在西北下角、上 = +y）；from/to 写反的取 min/size；
     * **UV 除以 4**：bbmodel 是像素（0..64）、原版是 0..16，原点都在贴图左上，所以**不翻转**；
     * **旋转**：单轴用原版 `element.rotation{origin, axis, angle, rescale:false}`，
       角度要**取反**（bbmodel 与 Minecraft 的旋转方向相反）；
     * **多轴**（这个模型有 2 个：Y90° + Z±22.5°）原版表达不了 → 把箱子**拆成 6 个单面 element**，
       每个面的 4 个顶点按顺序过一遍旋转矩阵，再取包围盒输出（面是平面，完全等价）；
     * **整体落到底面**：源模型最低点是 −0.287（四爪略低于底面），整体上移 0.287，
       让最低点正好落在 y=0 —— 对应老板要的"底座底面贴下方方块顶面"。
     结果：源 40 个元素 → 输出 **157 个 element**（13 无旋转 / 25 单轴 / 2 多轴拆面）。
249. **围盒与碰撞箱**（都从模型数据量出来，不写死）：
     几何 X 5.000..11.000、Y 0.000..15.787、Z 5.076..11.407（单位 1/16 格）
     → 碰撞箱 `Shapes.box(5/16, 0, 5.076/16, 11/16, 15.787/16, 11.407/16)`。
250. **朝向**：`facing` 属性（水平四向），放置时朝玩家；blockstate 里四个朝向各给一个 `y` 旋转，
     模型本身朝北做，不需要四套模型。
251. **彻底移除了 GeckoLib 链路**：删掉 `UniversalTerminalBlockEntity`、`UniversalTerminalRenderer`、
     `UniversalTerminalModel`、`UniversalTerminalRegistration`、`GeoModelBounds`，
     以及 `geo/`、`animations/` 资源；`build.gradle` / `mods.toml` / `gradle.properties` 里的
     GeckoLib 依赖也一并去掉 —— **回归"只依赖 NeoForge"**。
252. **验证**：`gradle build` 成功；`validate.py` 全过（顺手修了验证器：无命名空间的
     `parent: "block/block"` 现在按 `minecraft:` 处理）；jar 已装机（543,185 字节），

254. **症状一：黑紫方块**（模型加载失败）。日志：
     `JsonParseException: Invalid rotation -90.0 found, only -45/-22.5/0/22.5/45 allowed`
     —— **原版元素旋转只接受 0/±22.5/±45**（写死在 `BlockElement$Deserializer`）。
     修法：90° 和多轴的箱子一律**拆成 6 个单面 element**（把旋转烘进顶点，面是平面、完全等价）。
     `validate.py` 里加了对应检查（实测能抓到，见下）。
255. **症状二：零件乱飞 + 模型残缺**（老板截图：顶盖歪、冒出细条、形状不对）。
     根因是**我拍脑袋假设"bbmodel 与 Minecraft 的旋转方向相反"，于是给角度取了反**
     —— **这个假设是错的**：`java_block` 格式和原版是**同一套约定**。取反等于把每个旋转
     **镜像**，零件自然全飞了。
     怎么发现的：把源元素 `rot=[-22.5,0,0] origin=[7.5,-0.287,4.80709]`
     的顶点按两种约定各算一遍，只有**不取反**才能得到 y 0.000..0.924（爪子正好贴地）、
     并与"源模型整体包围盒"吻合。
256. **症状三：整个模型被凭空抬高 0.287**。根因是"落到底面"那段直接取
     `element["from"][1]` 当最低点 —— 但**带旋转的元素必须按旋转后的顶点算**：
     四爪的 `from.y = -0.287`，绕各自 origin 转 ±22.5° 之后**正好落在 y=0**，
     所以根本不需要上移。（第一版按 from 算，就把模型抬高了 0.287。）
257. **还踩了一个"自己骗自己"的坑**：为了核对转换结果，我写了个离屏渲染预览
     （`tools/compare_models.py`），结果**预览自己的 UV 单位就搞错了**
     （源是 0..64 像素、原版 JSON 是 0..16，我两边都除了 4 → 转换后那半边 UV 小 4 倍
     → 全采到透明像素 → 渲染成空白）。**白排查了一轮**。
     教训：**核对工具本身要先被核对**；能用数值判据就别用自己写的渲染器。
258. **最终数值核对**（`tools/verify_conversion.py` + 顶点级比对）：
     把转换后每个元素按它的 `rotation{origin,axis,angle}` 算回真实顶点，得到
     **X 5.000..11.000 / Y 0.000..15.500 / Z 5.117..11.555**，
     与源模型（X 5.000..11.000 / Y 0.000..15.500 / Z 5.117..11.554）**一致** ✓。
     碰撞箱就用这组数（按旋转后顶点算，**不能**直接取 from/to）。
259. **转换规则（最终版，写进脚本注释）**：
     ① 坐标**不平移**（java_block 就是方块坐标系）；
     ② UV **除以 4**、**不翻转**（两边原点都在贴图左上）；
     ③ 旋转角度**原样搬运、绝不取反**；只保留 0/±22.5/±45，其余拆面；
     ④ 落到底面要按**旋转后**顶点判断。
260. **验证**：`gradle build` 成功；`validate.py` 全过（含新增的旋转角检查）；
     jar 已装机（543,293 字节）。

### 2.47 原版模型最后一处：拆面时"薄板"位置和 UV 方向（老板截图：左右体块缺失）

261. **症状**（老板截图）：主体出来了，但**左右两侧的体块缺失、部分 UV 面也不对**。
262. **根因**：我"把旋转的箱子拆成面"那段写错了 —— 我是**取旋转后 8 个角的 min/max 当盒子**。
     但旋转 45° 的面，它的**包围盒比面本身大**，而且 4 个角只在特定位置贴到包围盒边界，
     于是画出来的薄片**位置偏、尺寸也不对**（表现就是缺块/错位）。
     正确做法：**恢复这个面旋转后的 4 个真实顶点**，按"它倾向哪根轴"输出一块薄板 ——
     薄板在平面内的两根轴用**真实顶点的范围**，法线那根轴取这 4 点的平均值再给极小厚度。
     这样薄板的两个面正好落在真实顶点所在的两个平面上，与原面**完全重合**。
263. **顺带修 UV 方向**：面被旋转 90°/180° 之后，UV 也得跟着转，否则那一面的贴图会歪 90°
     或被拉伸。做法：给每个面定一张"法线轴 / 平面内 u 轴 / 平面内 v 轴"的映射表
     （原则：从面外侧看，**u 向右、v 向上**），再用"旋转前后同一个顶点的位移方向"判断
     u/v 有没有翻转，翻转就用 min/max 交换表达（原版只要求 min/max 对，顺序无所谓）。
264. **核对**（仍用数值，不依赖我那个不可信的预览）：转换后按各元素 `rotation` 算回真实顶点，
     得到 **X 5.000..11.000 / Y 0.000..15.501 / Z 5.118..11.555**，与源模型一致 ✓；
     面数 **240 个（和源一致，一个不少）**；UV 全在 0..16 内；非法角度 0 个。
265. **验证**：`gradle build` 成功；`validate.py` 全过；jar 已装机（543,434 字节）。

### 2.48 【标准方案】装饰方块的"自定义建模 + 动画"——通用终端（最终可用版）

261. **结论先说**：要"**完全按建模的样子 + 自定义动画**"，用
     **GeckoLib + Blockbench 官方导出器**，并且**渲染器里什么都不做**。

262. **最终数据流**（全部由 Blockbench 官方导出，模组只做"搬运"）：
     ```
     .bbmodel（modded_entity / geckolib_model 格式）
        │  Blockbench → 导出 → "GeckoLib 模型"（geo.json）
        │  Blockbench → 导出 → "GeckoLib 动画"（animation.json）
        │  Blockbench → 导出贴图（png）
        ▼
     assets/<modid>/geo/block/<名>.geo.json            ← 骨骼 + 立方体（含任意角度旋转）
     assets/<modid>/animations/block/<名>.animation.json ← 关键帧（位置/旋转/缩放）
     assets/<modid>/textures/block/<名>.png
        ▼
     方块实体（GeoBlockEntity）+ GeoBlockRenderer 渲染
     ```

263. **模组侧只有 3 个类**（都放在 `client/gecko/` 或 `blockentity/`）：
     | 类 | 作用 | 关键点 |
     |---|---|---|
     | `XxxBlockEntity` | 模型 + 动画的挂靠 | `implements GeoBlockEntity`、`SingletonAnimatableInstanceCache`、`getTick` 返回 `level.getGameTime()` |
     | `XxxGeoModel` | 模型定义 | 继承 `DefaultedBlockGeoModel`，路径自动拼成 geo/block、animations/block、textures/block |
     | `XxxGeoRenderer` | 渲染器 | 继承 `GeoBlockRenderer`，**方法体里什么都不写** |

264. **⚠️ 最容易踩的 5 个坑（全部踩过，记牢）**：
     1. **渲染器不要自己平移** —— `GeoBlockRenderer.preRender` 内部已经
        `translate(0.5, 0.0, 0.5)`（因为官方 geo 是以**原点为中心**的坐标系）。
        自己再加一次 = 偏移翻倍，模型被推到方块边角。
     2. **渲染器不要自己旋转** —— GeckoLib 通过 `getFacing(T)` / `rotateBlock(...)` /
        `SUPPORTED_DIRECTION_PROPERTIES` **自动按方块的 FACING 属性旋转**。
     3. **几何不要自己平移** —— 官方导出就是"以原点为中心、底座在 y≈0"，直接用。
        （我曾按"方块空间"给它 +8，结果又偏了。）
     4. **动画别依赖 `triggerAnim`** —— 直接用控制器的状态处理器返回动画最稳：
        ```java
        controllers.add(new AnimationController<>(this, "main", 0,
                state -> state.setAndContinue(RawAnimation.begin().thenPlayAndHold("放置"))));
        ```
        （官方动画文件的 `loop` 就是 `hold_on_last_frame`，`thenPlayAndHold` 正好对应。）
        另外**别改官方 animation.json 的关键帧写法** —— 它必须是 `{"vector": [x,y,z]}`，
        自己转成裸数组 GeckoLib 会完全忽略（表现为"动画永远不动"）。
     5. **方块必须设 `RenderShape.INVISIBLE`**，否则方块自身模型会和 GeckoLib 渲染重叠。

265. **动画触发链路（缺一不可）**：
     ```
     方块类 getTicker()（仅客户端）→ 方块实体 clientTick() → 判断"刚放下" → 播动画
     ```
     我漏过一次 `getTicker`，结果 `clientTick()` 永远不被调用、动画永不触发。
     判定"刚放下"的办法：`onLoad()` 里记 `placedAt = level.getGameTime()`，
     客户端在 `placedAt` 之后的 15 tick 内播（避免退出重进又升一次）。

266. **可选依赖的正确写法**（GeckoLib 要能"没装也不影响其它功能"）：
     * `build.gradle`：`compileOnly files("libs/geckolib-neoforge-1.21.1-4.9.3.jar")`
     * `neoforge.mods.toml`：`modId = "geckolib"`、`type = "optional"`
     * **判断用单独的类**（只碰 `ModList`，不引用 GeckoLib 任何类型），
       渲染器注册/方块注册都包在 `if (available())` 里 —— 否则没装时类加载就崩。
     * 注册渲染器要在 `EntityRenderersEvent.RegisterRenderers`（不能在 mod 构造期取注册表，
       会报 `Trying to access unbound value`）。

267. **⚠️ 中文骨骼名/文件名完全没问题**（Blockbench 与 GeckoLib 都按 UTF-8 处理）。
     唯一真正被中文坑到的地方是 **`gradle.properties` 里的中文路径** ——
     Java 的 Properties 按 ISO-8859-1 读，必须写成 `\uXXXX` 转义。

268. **构建时必须注意**：改了包路径/移动了 Java 文件后，
     **要清 `build/classes` 缓存** —— 旧的 `.class` 会让编译"假装通过"，
     把真实错误藏起来（我就因此多绕了一轮）。

269. **验证顺序**（每步都有可查的证据，不靠猜）：
     1. `gradle build` + `python tools/validate.py`
     2. 装机后看日志：`[深空铸造体] 已启用 GeckoLib 渲染…`（注册成功）
     3. 放置方块 → 日志出现"触发动画"那行（触发成功）
     4. 游戏内看效果

270. **沿用同一方案的下一个模型，我需要的东西**：
     * `.bbmodel`（或 Blockbench 导出的 **geo.json + animation.json + png** 三件套）
     * 模型朝向（正面朝哪一边）—— 不对的话调 `rotateBlock` 之后的补偿角度
     * 方块本体尺寸（做碰撞箱用）

271. **不再使用的方案（留档，避免重走）**：
     * **GeckoLib + 自写转换脚本**：几何/动画自己转，UV 翻转、关键帧顺序、坐标翻转都错过；
     * **原版方块模型 JSON**：元素旋转只接受 0/±22.5/±45，多轴表达不了 → 27 个斜面做不出来；
     * **原版模型"烘成薄板"**：把旋转的箱子拆成面 → 斜面消失、贴图错乱；
     * **OBJ + NeoForge 的 `neoforge:obj` 加载器**：能出模型，但**没有骨骼信息**，
       部件归属只能靠几何猜（且路径要带 `models/` 前缀）；
     * **Flywheel（机械动力那套）**：技术上可行（Create 就是这么做的：模型拆部件 +
       每个部件一个 Instance + 每帧改变换矩阵），但要加编译依赖、且要自己写网格与动画，
       对"一个装饰方块"来说不划算。**最终选择了 GeckoLib，因为它把这两件事都做好了。**

### 2.49 【已跑通】带自定义动画的装饰方块 —— 完整配方与全部坑（通用终端最终版）

> 这一节是 2.48 的**修订与补充**。2.48 记的是"理论上该怎么做"，
> 这一节记的是**实测跑通的做法 + 一路上踩过的 9 个坑**。以后照这一节做。

#### 一、数据流（老板侧 / 模组侧分工）

```
老板在 Blockbench（GeckoLib 插件）里做模型 + 动画，导出三个文件：
    A. geo.json         ← 文件 → 导出 → GeckoLib 模型
    B. animation.json   ← 文件 → 导出 → GeckoLib 动画
    C. png              ← 贴图（导出时用的那张）

模组侧只做「搬运」，放到固定路径：
    src/main/resources/assets/<modid>/geo/block/<名>.geo.json
    src/main/resources/assets/<modid>/animations/block/<名>.animation.json
    src/main/resources/assets/<modid>/textures/block/<名>.png
```

#### 二、导入时的 4 项检查（写成了 `tools/import_new_terminal_model.py`）

272. **检查 1：动画在哪**
     * 先看 `geo.json` 顶层字段有没有 `animations`（一般没有）；
     * 没有的话看老板有没有单独导出 `animation.json`（**优先用官方的**）；
     * 都没有才从 `.bbmodel` 里生成 —— 但**别自己生成**，见坑 ③⑦。

273. **检查 2：贴图尺寸声明 —— 一个字都不要改**
     * `geo.json` 的 `description.texture_width/height` **不是** PNG 的实际像素尺寸，
       而是 **UV 的坐标系**，由 Blockbench 导出时决定，两者**可以不一致**（如 64 vs 128）。
     * 我曾"好心"把 64 改成 128 → 整个模型贴图乱成色块（现象：粉/绿错位）。

     > ✅ **2026-10-15 结论：这一条（273）原文是对的，不要改。**
     > 当天我曾在这里加过一段"更正"，说"两者可以不一致是错的、应该两个一起改"——
     > **那段话本身是错的，已删除**：照它做的结果是把声明的 64 改成 128，
     > 通用终端当场变成**整片花屏**（老板截图）。
     >
     > 字节码确认（`GeoQuad.build`，`javap -p -c`）：
     > `normalizedU = uv / texture_width` —— **声明就是 UV 空间的除数**。
     > 所以：**声明保持不变，PNG 用它的整数倍分辨率（1×、2×…）才是对的。**
     > 详见 **§2.57** 与 README 的**铁律 13**。

274. **检查 3：`format_version` 必须是 `1.12.0`**
     * GeckoLib 4.9.3 **只支持 1.12.0**。新版 Blockbench 导出会是 `1.21.110` 之类，
       此时日志出现：
       ```
       [GeckoLib WARN] Unsupported geometry json version for model <路径>. Supported versions: 1.12.0
       ```
       **几何被拒绝加载 → 模型能显示但动画完全无效**（本坑害我们绕了 4 轮）。
     * 两种格式的字段其实一样（`description`/`bones`/`pivot`/`cubes`/`origin`/`size`/`uv`），
       所以**直接改版本号字符串**即可，不必让老板重新导出。

275. **检查 4：动画名保持中文**
     * 骨骼名、动画名用中文**完全没问题**（Blockbench 与 GeckoLib 都按 UTF-8 处理）。
     * 我曾怀疑中文名导致缓存匹配失败而改成 ASCII —— **那是白改**，真凶是坑 ③。

#### 三、Java 侧只需要三个类（照抄即可）

276. **方块实体** —— `implements GeoBlockEntity`
     ```java
     private final AnimatableInstanceCache cache = new SingletonAnimatableInstanceCache(this);

     @Override
     public void registerControllers(AnimatableManager.ControllerRegistrar controllers) {
         // ★ 关键：状态处理器「每帧返回」动画（循环播放）—— 实测唯一稳定可行的写法
         controllers.add(new AnimationController<>(this, "main", 0,
                 state -> state.setAndContinue(RawAnimation.begin().thenPlay("放置"))));
     }

     @Override public AnimatableInstanceCache getAnimatableInstanceCache() { return cache; }
     @Override public double getTick(Object o) { return level == null ? 0 : level.getGameTime(); }
     ```

277. **模型** —— 继承 `DefaultedBlockGeoModel`，路径规则自动匹配上面三个文件：
     ```java
     public class XxxGeoModel extends DefaultedBlockGeoModel<XxxBlockEntity> {
         public XxxGeoModel() {
             super(ResourceLocation.fromNamespaceAndPath(MOD_ID, "universal_terminal"));
         }
     }
     ```

278. **渲染器** —— 继承 `GeoBlockRenderer`，**方法体里什么都不写**！
     ```java
     public class XxxGeoRenderer extends GeoBlockRenderer<XxxBlockEntity> {
         public XxxGeoRenderer(BlockEntityRendererProvider.Context ctx) { super(new XxxGeoModel()); }
     }
     ```
     居中由 `GeoBlockRenderer.preRender` 的 `translate(0.5, 0, 0.5)` 负责，
     朝向由 `getFacing` / `rotateBlock` / `SUPPORTED_DIRECTION_PROPERTIES` 负责。
     **自己再加一次就会翻倍**（现象：模型被推到方块边角）。

279. **方块本身**
     * `RenderShape.INVISIBLE`（画面全交给 GeckoLib，否则两套模型重叠）；
     * **必须实现 `getTicker`**（客户端），否则方块实体不会被 tick；
     * 右键打开菜单（`useWithoutItem` → `openMenu`）。

#### 四、九个坑（全部实际踩过，按"坑人程度"排序）

280. ① **`format_version` 不是 1.12.0** → 几何静默拒绝加载，动画完全无效
     （日志里只有一行 WARN，很容易漏看 → **每次都要 grep `GeckoLib.*WARN|ERROR`**）。
281. ② **改 `texture_width/height`** → 贴图全乱。
282. ③ **别用 `triggerAnim` + `PlayState.STOP`**：
     ```java
     // ✗ 实测无效（日志显示触发了，但模型一动不动）
     new AnimationController<>(this, "main", 0, state -> PlayState.STOP)
             .triggerableAnim("放置", RawAnimation.begin().thenPlayAndHold("放置"))
     // ✓ 有效
     state -> state.setAndContinue(RawAnimation.begin().thenPlay("放置"))
     ```
     * 顺带记：`triggerAnim` 在 `GeoBlockEntity` 上是**两个参数**(controller, anim)，
       没有 `(Player, ...)` 重载；`RawAnimation` 里是 `thenPlay` / `thenPlayAndHold` / `thenLoop`
       （**没有 `thenPlayX`**）。
283. ④ **自己从 `.bbmodel` 转动画容易把旋转符号转反**：
     bbmodel 内部用 `rotation_global` + 四元数，转成欧拉角时符号会翻。
     实测官方导出的爪1是 `+67.5`，我转出来是 `-67.5` —— **两只爪子方向相反**。
     → **一定要用官方导出的 `animation.json`**。
284. ⑤ **`loop` 值必须翻译**：bbmodel 里写 `hold`，GeckoLib 只认
     `default` / `play_once` / `hold_on_last_frame`（认不出会**静默回退**成 default）。
285. ⑥ **渲染器里不要做平移/旋转**（见 278）。
286. ⑦ **缺 `t=0` 关键帧**：Blockbench 各骨骼起点常不齐（主机 0.1667、爪2 0.0833…），
     导出后第 0 帧没有值。官方导出能用，但自己生成时必须补。
287. ⑧ **包路径写错 + 构建缓存**：移动 Java 文件后**必须清 `build/classes`**，
     否则旧 `.class` 会让编译"假装通过"，把真实错误藏起来（我因此白绕一轮）。
288. ⑨ **忘写 `getTicker`** → `clientTick()` 永不执行（动画触发链路断掉）。

### 2.50 【已跑通】收购投送机：放一次 / 卖一次 的动画（GeckoLib 动画的 5 个坑）

> 记录「收购站换模型 + 两个动画」从失败到成功的全过程。
> 一共踩了 **5 个坑，每个都会让动画"完全不动"，而且都不报错**。

**目标**：放下时播「放置」（0.75 秒）；每次成交播「投送」（0.21 秒）；
**播完再检测**（不是一直检测）；播完回到固定（展开）姿势。

#### 五个坑（按发现顺序）

293. **几何 `format_version` 必须是 `1.12.0`**
     Blockbench 新版会导出 `1.21.110`，而 GeckoLib 4.9.3 只认 `1.12.0` ——
     它**静默拒绝加载**，模型照常显示但动画完全无效。
     日志线索：`[GeckoLib WARN] Unsupported geometry json version ... Supported versions: 1.12.0`
     （两种格式字段相同，直接改版本号字符串即可。）

294. **贴图尺寸必须和 geo 声明的 UV 空间一致**
     geo 声明 `256×256` 而 PNG 是 `512×512` → UV 归一化后采样位置整体偏移，贴图错乱。
     修法：把 PNG **缩放到和声明一致** —— 不要去改声明（声明是 UV 坐标系，改了同样错）。

295. **不要用 `hasAnimationFinished()` 判断"播完了"**
     实测它在动画刚开始（动画队列还没填充）时**就返回 true**，
     阶段被瞬间判定"播完"，动画一次都没播出来（日志里全是「播放完毕（1 tick）」）。

296. **不要用 `isPlayingTriggeredAnimation()` 判断"是否正在播"**
     它只在用 `triggerAnim()` 触发时才为 true；
     而我们的动画是"状态处理器返回"驱动的，该方法**恒为 false**。

297. **动画阶段别放在"游戏 tick"上推进**（最坑的一个）
     * 方块实体的 `getTicker` **不保证每 tick 被调用**
       （实测控制器被调 1700+ 次，阶段一次都没推进）
     * 渲染帧率远高于 20，用 `level.getGameTime()` 做节流会丢帧 ——
       实测计数在 1~7 之间**反复回退**，永远到不了 18

     **正确做法**：阶段推进放进**渲染方法**（每帧必执行），
     并且**用墙上时钟 `System.nanoTime()` 计时**，不用 tick 计数：

     ```java
     // 渲染器：每帧推进一次
     @Override
     public void render(MachineBlockEntity be, ...) { be.clientAnimTick(); super.render(...); }

     // 方块实体
     public void clientAnimTick() {
         long nowNs = System.nanoTime();
         if (animOriginNs == 0L) animOriginNs = nowNs;                       // 定时间原点
         animAgeTicks = (nowNs - animOriginNs) / 50_000_000.0D;              // 给 GeckoLib 的时间轴
         long elapsedMs = (nowNs - animOriginNs) / 1_000_000L;
         // 用 elapsedMs 判断阶段是否结束
     }
     ```

298. **`getTick()` 不要返回世界总时间**
     GeckoLib 的 `adjustTick` 用 `delta = getTick() - manager.lastUpdateTime` 推进动画。
     老存档的世界时间动辄几万 tick，控制器刚建好时 `lastUpdateTime` 还很小 →
     第一帧算出"几万 tick"的 delta → **动画一步跳到结尾**。
     → 用本地计数器 / 墙上时钟换算的 tick。

#### 正确的整体结构

```
两个独立控制器（物理上不可能串轨）：
    "place"   只在 PLAYING_PLACE 阶段返回「放置」
    "deliver" 只在 DELIVERING  阶段返回「投送」

阶段机（时间全部来自 System.nanoTime）：
    PENDING ──100ms──→ PLAYING_PLACE ──750ms──→ WAITING_FIRST_DELIVER
                                                       │
                                             卖掉 ─────┘──→ DELIVERING ──210ms──→ WAITING_DELIVER
                                                                                  （之后只播投送）

服务端限流：notifySold() 每 400 ms 最多广播一次（否则成交刷屏会淹没客户端）
客户端排队：播放期间收到的成交通知 → pendingSold；当前动画播完若 pendingSold 就接着播
```

#### 调试方法（很有用）
`tools/render_geo_anim.py` 能把**指定 tick 的姿态离线渲染出来** ——
一眼看出动画数据本身对不对。当初就是靠它确认"数据没问题"，才把排查方向转到 GeckoLib 侧。

### 2.51 【已跑通】收购投送机定稿：收一次 = 播一次（握手式循环）

> 这一节是 2.50 的结局。2.50 记的是"怎么让动画能动"，
> 这一节记的是"怎么让收购动作和动画严格一一对应"——又踩了 4 个坑。

#### 最终行为（老板定稿）

```
容器里有东西
  → 一次收光【全部投料格子】（不是一格一格）
  → 播一次「投送」（0.5 秒）
  → 【等客户端回执"播完了"】
  → 再检查容器
      有东西 → 再收 + 再播
      没东西 → 不播、不收（空转明确跳过）
```

#### 又踩的 4 个坑

299. **`triggerAnim()` 的两参数版在客户端是空操作**（本次最坑）
     看 `GeoBlockEntity.triggerAnim` 的字节码：

     ```java
     if (level.isClientSide()) {
         getAnimatableInstanceCache()
             .getManagerForId(0L)              // ← 写死 ID = 0！
             .tryTriggerAnimation(controller, anim);
     } else {
         GeckoLibNetworking.triggerBlockEntityAnim(...);   // ← 客户端调这个 = 什么都不做
     }
     ```

     * 两参数 `triggerAnim(controller, anim)` 走**服务端分支** → 客户端调用无效；
     * 单参数版又**写死 `getManagerForId(0L)`**，而方块渲染器实际用的是
       `instanceId`（**方块坐标 hash**）—— 取到的不是同一个 AnimatableManager。

     **正确做法：自己拿对的管理器再触发**：

     ```java
     private void forceRestart(String controller, String anim) {
         var manager = animCache.getManagerForId(worldPosition.hashCode());  // 与渲染器同款 ID
         if (manager != null) manager.tryTriggerAnimation(controller, anim);
     }
     ```

     症状：**动画只有状态处理器第一次启动时播过一次，之后再也重启不了**（且不报错）。

300. **客户端渲染状态不能存 NBT**
     方块实体每次收到同步包都会 `loadAdditional`。把 `animPhase` 存进去 →
     每次同步都被重置回 PENDING、计时器归零 → 永远播不完、进不了下一阶段。
     现象：日志里「起始」一直跟着「elapsed」一起涨，"差"永远到不了阈值。
     → **动画阶段是纯客户端状态，不存 NBT**；用 `totalSold` 这类**服务端数据**判断"这台机器是不是用过"。

301. **不要用"格子空了"检测卖出**
     玩家自己把东西拿走也会让格子变空 → 误播动画。
     → 必须用**服务端信号**。

302. **两边各掐秒表必然打架**
     服务端按固定间隔收 + 客户端按动画时长播 + `pendingSold` 排队
     → 服务端收得比客户端播得快，攒下待播 → **"连着播两次、停一下"**。

     **正确做法：握手**。
     * 服务端：收一轮 → 等**客户端回执**（`BuyerAnimDonePayload`）→ 才收下一轮
     * 客户端：动画播完 → 发回执
     * **不排队**（播放期间到的成交信号直接忽略）—— 这是"一一对应"的关键
     * 服务端留**兜底超时**（1.5 秒），防回执丢包导致收购卡死

#### 最终时序

```
服务端 sellAllSlots() → notifySold() → BuyerSoldPayload → 客户端
客户端 onBuyerSold()   → 阶段进 DELIVERING → forceRestart() 重启动画
0.5 秒后               → 阶段回 WAITING_DELIVER → 发 BuyerAnimDonePayload
服务端 onAnimDone()    → animAckReady = true → 下一轮才被允许
```

### 2.52 【真凶】「放置」动画不播：不是 Java 的问题，是动画文件被 GeckoLib 整份拒收

> 这一节是 2.50 / 2.51 的**结案**。那两节一直在 Java 侧找原因（阶段机、握手、重启、兜底），
> 全都做对了 —— 但**动画从一开始就没被加载**，所以怎么改都不会动。
> 教训写在最前面：**「模型在、但完全不动」先查资源文件能不能被 GeckoLib 读进去，再查 Java。**

303. **症状**：收购投送机放下时不播「放置」；Java 侧日志一切正常
     （阶段机照走、`forceRestart` 照调、`播完 …约 550ms` 照打），但模型一动不动。

304. **证据链（关键一步：搜对了关键词）**。
     之前一直按 2.49 坑①说的搜 `GeckoLib.*WARN`，什么都没搜到就以为资源没问题。
     实际上这条是 **ERROR**，而且被别的模组几千行报错淹没了：

     ```
     [Worker-ResourceReload-6/ERROR] [GeckoLib/]: Unable to parse animation: 放置
     com.google.gson.JsonParseException: Invalid keyframe data - multiple starting keyframes?0.0
         at software.bernie.geckolib.loading.json.typeadapter.BakedAnimationsAdapter
            .getKeyframes(BakedAnimationsAdapter.java:114)
         at ...BakedAnimationsAdapter.bakeBoneAnimations(BakedAnimationsAdapter.java:77)
         at ...FileLoader.loadAnimationsFile(FileLoader.java:36)
     ```
     **异常一路冒到 `loadAnimationsFile`** ⇒ 不是"某一个动画坏了"，
     而是**整份 `buyer.animation.json` 都没进缓存** —— 「投送」也一样不存在。
     （日志里那些「收到售卖广播 → 播「投送」」是 Java 侧**决定**要播，
     不代表 GeckoLib 真的有动画可播。这就是为什么"日志全对、画面全死"。）

305. **规则（用字节码确认，不靠猜）**。`javap -p -c` 反汇编
     `BakedAnimationsAdapter.getKeyframes`，偏移 149~202：

     ```
     tick = readTimestamp(entry.getKey())
     if (tick != 0.0)         goto 203   // 正常处理
     if (list.isEmpty())      goto 203   // 正常处理（说明 0.0 是第一个）
     throw new JsonParseException(
         "Invalid keyframe data - multiple starting keyframes?" + key)   // ← 180~202
     ```

     **读法：GeckoLib 根本不会给关键帧排序，它就是按 JSON 的书写顺序读。
     只要某个通道里 `"0.0"` 不是第一项，就抛异常，整份文件作废。**

306. **本项目的病灶**：`buyer.animation.json` 的「放置」里，
     `固定杆` / `固定杆2` / `固定杆3` / `固定杆4` 四条 `position` 通道的键顺序是

     ```
     "0.3333" → "0.5833" → "0.0"      ← 0.0 排在最后，踩中规则
     ```

     （Blockbench 手工调整过关键帧顺序，或在最后补了一个 0.0 起手帧，就会这样。）
     「投送」的两条通道是 `0.0 → 0.2083 → 0.5`，**顺序正常**——
     所以当时"投送看起来是好的、只有放置不播"这个现象具有极强的误导性：
     **实际是整份文件一起废**，只是「投送」本来就短、又常常和「放置」混着看，不容易分辨。

307. **修法（只动顺序，绝不动数值）**：`tools/check_gecko_animations.py --fix`
     把每条通道的键按**时间升序重排**。修完脚本会自我校验
     「重排前后的 JSON 语义完全一致」，不一致就拒绝写盘。
     本次结果：`json.load(修前) == json.load(修后)` → **True**；
     文件行**多重集**不变（`Compare-Object` 差异 0 行）⇒ 只有顺序变了。
     > 这属于"格式修正"，不属于动老板的建模数据（§9.4 允许）。

308. **新增的自检**（以后每次改动画都要跑）：
     * `python tools/check_gecko_animations.py` —— 检查 4 条规则：
       ①`"0.0"` 必须第一项（本坑）②时间必须递增 ③`loop` 只能是
       `default`/`play_once`/`hold_on_last_frame` ④`vector` 必须是 3 个数；
     * 已把"动画文件过 GeckoLib 规则"加进 `verify_readme_claims.py` 的断言表
       （35 条 → **37 条**）；
     * 日志里改成专门搜 **`Unable to parse animation`**，不要只搜 `GeckoLib.*WARN`。

309. **一句话总结给下一次的自己**：
     **"模型在，但一动不动" → 先搜 `Unable to parse animation` + 跑
     `check_gecko_animations.py`，再去碰 Java。**

### 2.53 【真凶】动画"播两次 / 播到一半重置"：触发式动画播完会被再请求一次

> 2.52 修好"动画根本不播"之后，老板立刻报了下一个现象：
> **"会重叠播放两次，视觉上是第一次播放到一半重置播放第二次。"**
> 这一节记录它的根因（字节码级）与修法。**结论：错在"用触发式动画重启动画"这个做法本身。**

310. **症状**：动画确实播了，但一次触发会播**两遍** —— 第二遍从第 0 帧开始，
     通常只播一小段就被相位结束掐掉，看上去就是"跳回开头重播"。

311. **怎么排除掉其它嫌疑的**（都查过，都不是）：
     * **相位机没问题**：日志里 `PLAYING_PLACE: elapsed=0 → 300 → 594` 单调递增，
       到 800ms 才 `「放置」播放完毕`，**相位内部没有任何重置**。
     * **握手没问题**：客户端播完 → 回执 → 服务端 `记下「放置」已播完`，一次对一个。
     * **不是"格子空了"误触发**、也不是同步包重置相位（那些是 2.51 的坑，已修）。

312. **真凶（`javap -p -c` 反汇编 `AnimationController`，偏移 0~85）**：

     ```java
     protected PlayState handleAnimationState(AnimationState<T> state) {
         if (this.triggeredAnimation != null) {                       // 触发式动画在播
             if (this.currentRawAnimation != this.triggeredAnimation)
                 this.currentAnimation = null;
             setAnimation(this.triggeredAnimation);
             if (!hasAnimationFinished()) { ...; return PlayState.CONTINUE; }
             this.triggeredAnimation = null;
             this.needsAnimationReload = true;                        // ★ 播完就置位
         }
         return getStateHandler().handle(state);                      // ★ 然后再问状态处理器
     }
     ```

     而我们用的是"**状态处理器 + 触发式动画**"两套并用：
     * 状态处理器负责"这个相位期间该有动画"（相位没结束时一直返回 `setAndContinue`）；
     * `forceRestart` 负责"把动画从头开始播"（当时用的是 `tryTriggerAnimation`）。

     **于是动画播完的那一帧必然出事**：相位还没结束（「放置」相位 800ms，动画只有 750ms），
     状态处理器**又返回同一个动画**；`setAnimation` 一看 `needsAnimationReload == true`
     就**不早退**（偏移 21~36 的 `ifne`），直接重建队列、`shouldResetTick = true`
     → **动画从第 0 帧重播**。这就是"第二次播放"。

     > 注意这里有个**时序巧合**让它更容易发生：相位时长（800 / 550）都比动画时长
     > （750 / 500）**长 50ms** —— 正好留出一个"动画已播完、相位还没结束"的窗口。

313. **修法（改一行语义，不碰相位机）**：把"重启动画"的手段从
     "登记触发式动画"换成"**只置控制器的重载标志**"：

     ```java
     // 旧：产生触发式动画 → 播完必然触发上面的路径
     // manager.tryTriggerAnimation(CTRL_PLACE, ANIM_PLACE);

     // 新：只置一位，让状态处理器自己重建一次
     var controller = manager.getAnimationControllers().get(controllerName);
     controller.forceAnimationReset();     // 方法体就一句：needsAnimationReload = true
     ```

     `setAnimation` 重建后会把 `needsAnimationReload` 清回 `false`（偏移 93~95），
     所以**只重建一次**；之后相位期间每帧的 `setAndContinue` 都会早退（偏移 21~36），
     动画稳定播完、停下、回到固定姿势。**全程没有触发式动画，也就没有"再被请求一次"。**
     同时把两个控制器的 `.triggerableAnim(...)` 注册**删掉**（已经没有调用方）。

314. **为什么当初会用触发式动画**：2.49 坑③ 记录过"状态处理器返回 STOP + `triggerableAnim`
     实测不动"，2.51 坑 299 又发现 `triggerAnim()` 两参数版在客户端是空操作 ——
     于是演变成"状态处理器驱动 + `tryTriggerAnimation` 重启"。
     这个组合**每个单独看都有理由，合在一起就必然双播**。
     正确的分工是：**状态处理器负责"要不要有"，`forceAnimationReset` 负责"从头播"**。

315. **新增的自检**：`verify_readme_claims.py` 加了 3 条断言（37 → **40 条**）：
     ①`forceRestart` 用的是 `forceAnimationReset` 且代码里不再出现 `manager.tryTriggerAnimation`；
     ②两个控制器都不再注册 `triggerableAnim`；③"首次渲染兜底"日志带实例标识。

316. **留了个"方块实体是否被重建"的探针**：第一次测试的日志里，同一个位置
     `-237,64,-877` 的「首次渲染兜底」出现了 **16 次、每次 `elapsed=0`**，
     说明**客户端方块实体被反复重建**（`animOriginNs` / `placeAnimTriggered` 都是纯 Java 字段，

     若下次日志里实例号不变、兜底只出现一次，则说明那 16 次只是老板反复拆放机器导致的，属正常。

### 2.54 载具打印机：12 格"缺一不放"，且不允许别的结构重叠

> 老板反馈："载具打印机的碰撞箱会被其他多方块结构挤掉，让载具打印机无法放置在别的方块
> 重叠碰撞箱的位置，并且让别的多方块结构也不能和载具打印机重叠放置。"
> 定稿方案（老板选项 3 + 两点修改）：**全有或全无，且不给提示，也不允许重叠。**

317. **现象与真因**：打印机占 3×2×2 = 12 格（1 格控制器 + 11 格结构件）。
     旧实现是"**被挡的格子跳过**"（`setPlacedBy` 里 `if (!canBeReplaced()) continue;`），
     于是被别的方块/别的多方块结构占住的格子**没有结构件** →
     **那一格没有碰撞** → 整台机器的碰撞箱**缺一块**（老板说的"被挤掉"）。
     反方向也成立：结构件是实心、不可覆盖的方块，别的结构自然也放不进来。

318. **定稿行为**（改动只有一处，在 `MachineBlock.getStateForPlacement`）：

     ```java
     // 12 格里只要有一格放不下，就整台不放下（连控制器也不放）
     if (kind == MachineKind.CORE
             && !PrinterPartBlock.canPlaceAll(context.getLevel(), context.getClickedPos(), facing)) {
         return null;      // ← 原版 BlockItem.place 见到 null 直接 FAIL
     }
     return state;
     ```

     * 返回 `null` 的效果：`BlockItem.getPlacementState` 返回 null →
       `BlockItem.place` 直接返回 `InteractionResult.FAIL` →
       **什么都不放、不消耗物品、不报错、不提示**（老板明确要求"不给提示"）。
     * `canPlaceAll` 检查的是**以控制器为原点的 12 格**（结构件与控制器定义见 `PrinterStructure`），
       控制器是 **part 3**（偏移 `(0,0,0)`）—— 注意 `OFF_Z = {-1,-1,-1,0,0,0}` 里
       第 0 列偏移是 `-1`，所以**控制器不在结构的角上随便一格，而是 X 居中、Z 靠前那一列**。
     * `setPlacedBy` 里的 `canBeReplaced` 跳过**保留**，降级为"保险"：
       正常流程永远走不到（放置前已经全查过），但万一有别的途径绕过放置检查，
       **宁可直接少一格，也绝不吞掉别人的方块**。

319. **为什么不选另外两种**（留档，避免以后反复讨论）：
     * **"填充格不挡路 + 碰撞箱由控制器统一提供"**：碰撞箱确实永远完整，
       但需要给控制器一个**覆盖 12 格**的碰撞形状 —— 本项目踩过这个坑
       （见 `MachineBlock.CORE_SHAPE` 的注释：超出方格的碰撞会挡住旁边一片区域）。
       而且老板要的是"**不允许别的结构重叠**"，这条正好相反。
     * **"放置时顶掉挡路的方块"**：会拆掉玩家自己的建筑/别的机器的部件，风险太大。

320. **代价（已知，老板接受）**：贴着墙/别的机器放打印机时，会**安静地放不下去**，
     玩家看不到任何原因。若以后觉得困惑，最小改动的补救是加一个**音效或动作栏提示**
     （一行消息即可），不需要动放置逻辑。

321. **新增自检**：`verify_readme_claims.py` 加 2 条（40 → **42 条**）：
     ①放置前确实查了 `canPlaceAll(context.getLevel(), context.getClickedPos(), facing)`；
     ②控制器那一格仍是 `CORE_SHAPE = Shapes.block();`（实心、不给别人重叠）。

### 2.57 【定论】geo 声明是 UV 空间的"除数"—— 声明不能改，只能让 PNG 是它的整数倍

> 承接 §2.56。上一节按"PNG 和声明要一致，且要一起改"的思路把声明从 64 改成 128，
> 结果**通用终端整片花屏**（老板 2026-10-15 游戏截图，绿/粉/蓝色块）。
> 这一节用字节码把规则钉死，并纠正 §2.56 第 332 条。

336. **字节码证据**（`javap -p -c`，GeckoLib 4.9.3）：

     ```text
     // software/bernie/geckolib/cache/object/GeoQuad.build(...)
     //   参数：...(float u, float v, float uSize, float vSize, ...,
     //           float textureWidth, float textureHeight, ...)

        0: fload_1          // u
        1: fload_3          // uSize
        2: fadd             // u + uSize
        3: fload 6          // textureWidth      ← 来自 geo 的 description.texture_width
        5: fdiv             // (u + uSize) / textureWidth
        ...
       17: fload_1          // u
       18: fload 6          // textureWidth
       20: fdiv             // u / textureWidth  ← 归一化
       22: fload_2 / 23: fload 7 / 25: fdiv      // v / textureHeight
     ```

     调用链也确认了：`BakedModelFactory$Builtin.constructCube` 把
     `ModelProperties.textureWidth()/textureHeight()` **当参数传给** `buildQuads` → `GeoQuad.build`。

     **结论：`normalizedU = uv / texture_width`。声明是除数，就是 UV 坐标系本身。**

337. **所以只有"整数倍"这一个正确关系**：

     | 配置 | 归一化 | 采样点（UV=40，原图 128）| 结果 |
     |---|---|---|---|
     | 声明 64 + PNG 64（整图缩小的那份）| 40/64 = 0.625 | 0.625×64 = 40 px（= 原图 80 px）| ✅ 对，但**分辨率被砍半** |
     | 声明 **128** + PNG 128（§2.56 第 332 条的做法）| 40/128 = 0.3125 | 0.3125×128 = **40 px** | ❌ **只采到一半区域 → 花屏** |
     | **声明 64 + PNG 128（定稿）** | 40/64 = 0.625 | 0.625×128 = **80 px** | ✅ **同一块图案、两倍分辨率** |

     > 关键就一句话：**UV 值（40）不变，声明不变，采样点随 PNG 尺寸等比放大。**
     > 上一节的错误在于把声明也改了 —— 那等于把"尺子"换了长度。

338. **定稿改法（只有一步）**：

     ```text
     textures/block/universal_terminal.png  ← 换成 128×128 原图（直接复制，零重采样）
     geo/block/universal_terminal.geo.json  ← 【一个字都不要动】，texture_width/height 保持 64
     ```

### 2.58 星联动力联盟商店：新模型 + "靠近展开 / 离开闭合"动画

> 老板 2026-10-16 自己建模了星联动力联盟的商店，要求：
> "玩家靠近 2 格内播放展开动画停止在最后一帧，离开两格范围播放闭合动画停止在最后一帧，
> 只有等某个动画播放完毕后才可播放另一个动画，不要让它们冲突导致频繁触发。"

341. **导入**（新脚本 `tools/import_astralink_shop_model.py`）：

     | 资源 | 来源 | 注意 |
     |---|---|---|
     | geo | `半成品\动态建模\星联动力联盟商店\…geo.json` | `format_version` 已是 1.12.0 ✓；`identifier` 改成 `geometry.terminal_astralink`；**`texture_width/height = 256` 一个字没动** |
     | 动画 | 同目录 `…animation.json` | **展开 / 闭合**，各 0.5s，`hold_on_last_frame`；关键帧 `"0.0"` 都在第一项 ✓ |
     | 贴图 | **从 bbmodel 里取内嵌的 base64** | 512×512、只有 13 色；对声明 256 是 **2×** ✓（铁律 13：声明不动、贴图取整数倍）|

     模型名定为 **`terminal_astralink`**（geo / animation / texture 三个文件同名，
     GeckoLib 的 `DefaultedBlockGeoModel` 就是按这个名字拼路径的）。

342. **适用范围**：老板选的是"**只星联的商店，三个等级都用这套**"。
     所以判断必须带上公司：`MachineGeoModel.geoName(be)` 里
     `case TERMINAL -> Company.ASTRALINK == be.company() ? "terminal_astralink" : null`。

     > ⚠️ 这里有个**必须成对修改**的地方：`MachineBlock.hasCustomModel(BlockState)`
     > （决定本体 RenderShape 是 INVISIBLE 还是 MODEL）和上面那个
     > `MachineGeoModel.geoName(方块实体)` 判断必须一致。
     > 一边认为"有模型"、另一边认为"没有"，就会出现**本体和模型同时画**（重影），
     > 或者**两边都不画**（方块隐形）。

343. **触发链路**（服务端定事实、客户端播动画 —— 和收购站一个思路）：

     ```
     服务端 每 5 tick（0.25 秒）
       MachineBlockEntity.updateAnyoneNear()
         · 水平距离 ≤ 2 格（忽略高度）；旁观者不算
         · 只有变化才 setChanged() + syncToClient()   （NBT 字段 AnyoneNear）
     客户端 每帧
       TerminalShopAnim.tick()   ← 挂在 shop 控制器状态处理器上（每帧必到的心跳）
         · 正在播 → 直接 return：**绝不打断**
         · 播完了 → 落实状态；若这期间目标变了，紧接着播反向动画（= 排队，不丢切换）
         · 尚未播过 + 状态是闭合 → 状态处理器返回 STOP（模型静止姿势本来就是闭合）
     ```

     * **为什么算服务端**：谁在附近是服务端的事实（客户端不一定知道所有玩家）；
     * **为什么每 5 tick**：不必每 tick 遍历玩家列表，0.25 秒的响应肉眼无感；
     * **为什么"排队"而不是"丢弃"**：玩家进进出出时若直接丢弃切换请求，
       商店最后可能停在错误状态（人就站在旁边却关着）。

344. **三个必须避开的坑**（实现里都处理了，留档）：

     * ⭐ **必须推进 GeckoLib 的时间轴**（最阴的一个，2026-10-16 实测踩到）：
       `getTick()` 返回的是 `animAgeTicks`，而这个字段原先**只有收购机的
       `clientAnimTick()` 在更新**（渲染器 `if (isBuyer())` 和客户端 ticker 都只认 BUYER）。
       商店不推它 ⇒ 时间轴恒为 0 ⇒ `AnimationController.adjustTick` 每帧算出的
       `delta = getTick() - lastUpdateTime` 恒为 0 ⇒ **动画永远停在第 0 帧**。
       而「展开」的第 0 帧**正好是闭合姿势**，所以画面上看起来"根本没播"；
       更坑的是**状态机日志一切正常**（那套用自己的墙上时钟计时，与 GeckoLib 无关）。
       修法：`MachineBlockEntity.advanceAnimClockOnly()`，在 `TerminalShopAnim.tick()` 里每帧调一次。
     * **静止姿势 = 闭合姿势**：状态处理器若一上来就返回「闭合」，
       那么每次进游戏（区块加载）模型都会从"展开姿势"滑回"闭合姿势"——
       没人碰它却自己关一次。修法：`everShown` 标志，没播过任何动画时返回 `PlayState.STOP`。
     * **重启必须用 `forceAnimationReset`**（铁律 12）：`restartAnimation` → `forceRestart`
       → `controller.forceAnimationReset()`。用触发式动画的话，动画播完时 GeckoLib 会置
       `needsAnimationReload` 并**再问一次状态处理器**，同一个动画被重建、又播一遍 ——
       正是老板说的"冲突 / 频繁触发"。

     > 📌 **这次的定位方法值得复用**：先看日志 —— 36 条 `[商店动画]` 记录证明
     > "服务端检测 → 同步 → 控制器回调 → 状态机切换"整条链路都是通的，
     > 于是问题必然在"动画被请求了但没走时间"这一层，而不是在触发逻辑里。
     > **日志把范围缩小到一层，再去读那一层的字节码/源码**，比通读全部代码快得多。

345. **隔离**（老板前一天刚提的要求，这次直接照做）：

     * 动画逻辑单独一个类 `client/gecko/TerminalShopAnim.java`，**不和收购机那套相位机混**；
     * `shop` 控制器**只给 `kind() == TERMINAL` 注册**（`registerControllers` 里判种类），
       收购机和载具打印机连这个控制器都没有；
     * 资产各占各的文件（`terminal_astralink.*`），导入脚本单独一个
       （`import_astralink_shop_model.py`），改它不影响别的模型。

346. **新增自检 5 条**（49 → **54 条**）：模型按"种类 + 公司"挑且贴图独占、
     动画是 HOLD_ON_LAST_FRAME、正在播时不被打断、重启走 `forceAnimationReset`、
     `shop` 控制器只注册在 TERMINAL 上。
